# Changelog

All notable changes to @reactre/dom, @reactre/core, @reactre/compiler, @reactre/compat, @reactre/full-compat, @reactre/plugin and @reactre/preact are recorded here. The packages are released together, at the same version.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Every package

- Changed: the repository is Bun and TypeScript only, and CI no longer installs Node. `packages/plugin/test/dist.ts`, run by Bun, replaces `test/node.mjs`: it installs the packages' dist builds into a temp folder, with export conditions that leave out `bun` and `reactre-source`, and checks the plugin there in Vite builds, an SSR build and Vite's dev server. `scripts/consumer.ts` installs the packed packages with `bun install` and type-checks the user's project with `bun check`, not tsc, `skipLibCheck` still off. The test fixtures and the benchmark's React app are `.tsx` files, and the two JavaScript modules `test/missed.test.ts` needs are written to a temp folder when it runs. @reactre/plugin and @reactre/preact drop their `engines.node` field, and the READMEs their npm install lines and notes on Node. What the packages do is unchanged: they still compile `.js` and `.jsx` files, and @reactre/compat still maps `react-dom/server.node`.

### @reactre/core

- Changed: a spread prop that is an inline event-handler attribute, in any case (`onclick`, `ONCLICK`, `onerror`), with a string value (`{ onclick: "alert(1)" }`, from data) is left out: written as an attribute, the page would run it as code. The client leaves out such a key when the element has it as a handler property (`"onclick" in node`); the server, with no element to ask, when it is one of the inline handler names of the HTML standard and browsers, whatever its value. Another key that starts with `on` (`one`, `online`) is still an attribute, a function still listens in camelCase (`onClick`), and null still removes an attribute. The development build warns `STRING_HANDLER` for each element where it leaves one out. Compiled props, not spread (`onClick={fn}`), and @reactre/compat, which follows React, are unchanged.
- Added: `createRoot(fn)` in `@reactre/core/features/owner`, which runs `fn(dispose)` under a new owner; `dispose` stops the effects and runs the cleanups `fn` made. As in Solid 2.0, a root made inside an owner is disposed with it; one made under `runWithOwner(null, ...)` lives until `dispose`.
- Added: `getOwner()` and `runWithOwner(owner, fn)` in `@reactre/core/features/owner`, to make things later that belong to an owner kept from earlier. `runWithOwner` runs `fn` untracked; with null, what `fn` makes belongs to nothing.
- Added: `onSettled(fn)` in `@reactre/core/features/timing`, Solid 2.0's replacement for `onMount`. `fn` runs once, untracked, under the owner it was called in: at the end of the batch or `flush` it was called in, or else in a microtask, so in a component, once its view is in the page. A function it returns is a cleanup of that owner.
- Added: `flush(fn)` and `flush()` in `@reactre/core/features/timing`, Solid 2.0's replacement for `batch` (which stays). `flush(fn)` runs `fn` and applies its writes before it returns, inside an outer batch too; `flush()` applies what the current batch has queued so far, and outside a batch does nothing.
- Added: `reaction(compute, apply)` in `@reactre/core/features/reaction`, an effect in two halves, as Solid 2.0's `createEffect(compute, apply)`: `compute` is tracked, and `apply(value, prev)` runs untracked when its value changes, returning a cleanup if it likes. `effect(fn)` is unchanged.
- Changed: these are feature modules, not exports of `@reactre/core`, whose main entry keeps 0.0.3's runtime API (it gains only the compiled-away control flow below), and none hooks into the code that runs without it. An app that does not import them ships the same code as with 0.0.3: the existing size profiles' bundles are the same code, byte for byte, once local names are left unminified, and the same size minified. Their gzipped sizes are 0.0.3's, or a few bytes off, as Bun's minifier picks local names from the letters of the whole source file, code it drops included. `test/features.test.ts` adds three profiles for them: `root`, `settled` and `reaction`.
- Added: `<Show when fallback keyed>`, `<Switch fallback>` with `<Match when keyed>`, `<Repeat count from fallback>`, `<Portal mount>` and `<Dynamic component>`, as Solid 2.0 has them, and a `fallback` on `<For>`, shown while `each` is empty. They are compiled away: an app that uses none of them ships none of them, and one that does ships no runtime of theirs. A `<Show>` rebuilds its children only when `when` turns truthy or falsy (with `keyed`, for every new value), and a function child gets an accessor of the value; a `<Switch>` rebuilds only when another `<Match>` becomes the first truthy one. `test/features.test.ts` adds a `show` profile, an app with a `<Show>`, a `<For>` fallback and a class list.
- Added: `dynamic(source)` in `@reactre/core/features/dynamic`, a component that renders the component or tag name `source` returns. It runs, so it is a feature module; `<Dynamic>` and the types both take (`DynamicComponent`, `PropsOf`) are in `@reactre/core`.
- Added: JSX types for them, and for `class` as an object or an array, `ref` as an array of refs, and `defaultValue`, `defaultChecked`, `defaultSelected` and `defaultMuted`. Each control flow element throws when called, naming the compiler and the import it looks for.
- Added: Solid 2.0's stores in `@reactre/core/features/store`. `createStore(value)` returns a deep reactive proxy, whose reads subscribe to the property read alone (an array's by index and `length`, an object's keys by a signal of their own), and a draft-first setter, `setStore((s) => { s.todos.push(todo) })`, whose writes are batched; an object the setter returns replaces the store's contents shallowly. `createStore(value, { shallow: true })` is a one-layer store, `createStore(fn, seed)` a derived store that can be written, and `createProjection(fn, seed, { key })` a read-only one, into which what `fn` returns is reconciled. `reconcile(value, key)` writes only what differs, keeping objects of the same key ("id", or null for by index); `snapshot` and `deep` return plain copies, `deep` after subscribing to everything; `merge` and `omit` are Solid 2.0's props helpers, whose properties are getters of their sources. In TSX, a read through a store is reactive (see @reactre/compiler below): `{store.count}`, `<Show when={store.user}>`, `<For each={store.todos}>` (which follows pushes, removals and moves) and a `<For>` row's hole that reads only its item (`t.done`) all follow the store. The README's store section lists what the compiler cannot follow to a store, which is written once.
- Added: `memo(fn, { equals })` and `signal(fn)` in `@reactre/core/features/memo`, under core's names, as Solid 2.0's options for them. `memo`'s `fn` is given its last value, `equals` decides whether its readers re-run (`false`: every time), and `signal(fn)` is a writable derived signal: `fn(prev)` recomputes it when its sources change, and a write sets it until then. `signal(value, { equals })` takes the option too, and both take Solid 2.0's `lazy` and `unobserved` (see below).
- Changed: both are built from `@reactre/core`'s public API, and ship only with their import: the existing size profiles are unchanged. `test/features.test.ts` adds two profiles for them: `store` and `memo`.
- Added: `path(...keys, value)` in `@reactre/core/features/store`, Solid 2.0's `storePath`: a setter's function that writes one value at a path, as Solid 1.x's `setStore("user", "name", "Ada")` did, `setStore(path("user", "name", "Ada"))`. A step is a key, an array of keys, or in an array a range `{ from, to, by }` or a test `(item, index) => boolean` of its items; the value is a value, a function of the one there (returning it unchanged writes nothing), an object merged into the object there (symbol keys and getters too), or `path.DELETE`. With no key, the value is merged into the store. `__proto__`, `constructor` and `prototype` are neither followed nor written. An app that does not use it ships none of it: the `store` and `storeEach` profiles are the same code, byte for byte with local names left unminified.
- Added: `createContext(default?)` and `useContext(ctx)` in `@reactre/core/features/context`, Solid 2.0's context. A context is a component, `<Ctx value={v}>children</Ctx>`, with no `.Provider`; what its children make finds the value then and later (a slot's next content, a `<For>`'s next row, an effect's next run). `useContext` returns the nearest provider's value, else the default, and throws `ContextNotFoundError` for a context without a default; a provider of `undefined` is no provider.
- Added: `<Errored fallback>` in `@reactre/core/features/errors`, Solid 2.0's error boundary: its children, or the fallback (an element, or `(err, reset) => ...`) once something they made throws while it is built or while it updates (a component's body, an effect's or a slot's run, a `<For>` row). What the children made is disposed; `reset()` builds them again. Beside it, `effect(fn, { error })`, the core's `effect` with a handler for what its runs throw, and `configureClientErrors({ onError })`, which gets what no boundary catches; without either, errors are thrown on as before.
- Changed: nothing for an app that imports neither. A provider and a boundary read `props.children` inside themselves, so they need their children unbuilt; the compiler passes JSX children as a getter (lazy children, below), so `<Ctx value="dark"><Label /></Ctx>` and `<Errored fallback={...}><Child /></Errored>` work as written, and a boundary catches a throw in its child's component body. Both read their children in a slot, so a child that may change (`{more() ? <A /> : null}`) is read again under them. Each module installs itself as it loads, by wrapping methods of the core's owned effect class (and, for errors, of its row observer class, now exported as the internal `__RowObserver`, beside `__Owned`): an app that imports neither ships the same code as before, byte for byte with local names left unminified and the same size minified; gzipped, the benchmark app and `reaction` are 1 byte larger, as Bun names locals by the letters of the whole source. `test/features.test.ts` adds two profiles, `context` and `errors`.
- Changed: props are reactive, as in Solid. A component still runs once; a prop passed an expression that calls a function (`<Label text={name()} />`) updates the holes that read it (`{props.text}`), and children that hold JSX are built when the component reads `props.children`, after its own code before that, so a provider can set up first. Destructured props (`({ text }) =>`) are read once, when the component runs; the store's `merge` and `omit` keep them reactive, in holes that read what they return and in spread props. Props a component passes on to another (`<Theme value="dark">{props.children}</Theme>`) stay getters, so children are built inside the component they are passed to. The types are unchanged: props are typed as values. The README has a Props section.
- Added: `__props`, which merges a component call's spread props keeping their getters, so `<Child {...props} />` passes reactive props on. It is in a bundle only where compiled code calls it. The size profiles that pass no prop reactively or lazily are unchanged, byte for byte; `context` and `errors` are now written as JSX, `<Theme value="dark">` and `<Errored fallback>` with JSX children, and `test/features.test.ts` adds a `props` profile, an app that passes props reactively, spreads them and builds children lazily.
- Added: Solid 2.0's async data in `@reactre/core/features/async`. A memo may return a Promise or an async iterable (`memo` here is the core's, typed for it); a read before it has a value is not ready, and `<Loading fallback on>` shows `fallback` until nothing its children read waits, building them off the page meanwhile. An update that makes an async memo compute again is a transition: the effects it would run are held, so the page keeps its old values until the new ones have come. `isPending(fn)` is true while a change to what `fn` reads is in flight, `latest(fn)` reads past the hold, `resolve(fn)` is a Promise of a value once nothing is pending, `refresh(memo)` computes it again quietly, `<Reveal order>` orders sibling boundaries, and `lazy(load)` loads a component. `NotReadyError` is what a read throws where nothing waits for it.
- Added: Solid 2.0's actions in `@reactre/core/features/actions`. `action(function* () {...})` runs a generator (or an async generator) in the transition, awaiting what it yields; `createOptimistic(value | fn)` and `createOptimisticStore(value | fn, seed)` take writes that show at once in an action's code and revert when the transition ends, a store's `fn` may be async, and `refresh` runs it again; `affects(target, key?)` marks what an action changes as pending; `until(fn, { timeout, signal })` waits for a condition, reading optimistic values as their base.
- Changed: both need the core's async runtime, which is a build of its own, `dist/async`, resolved by the `"reactre-async"` export condition (and by `"development"`). The default build is made from the same source with the runtime's code stripped (`// #if ASYNC` blocks in `src/index.ts`), so it is the same code as before, byte for byte, and so is every size profile and the benchmark app. Imported with the default build, either module throws, naming the plugin and the condition. Bun resolves the sources, which hold the async runtime: a `Bun.build` through either plugin strips it from them for a program that imports neither module, and `bun run` and `bun test` run them as they are, the async runtime inert until one of the modules loads. Where they differ from Solid 2.0: writes apply at once and a transition holds effects only; one transition is open at a time; `isPending` is false for a plain signal; a slot that runs again and reads something not ready keeps its old nodes, frozen; a memo made before the module loads stays plain; code after an `await` in an async generator action runs outside it; and `createStore` and `createProjection` take no async function (use `createOptimisticStore`). `test/features.test.ts` adds two profiles, `async` and `actions`.
- Added: `<For each keyed={false}>`, Solid 2.0's replacement for `<Index>`: rows by position. The row at index `i` is built once and stays while the list is that long; it gets an accessor of its item and the index, `(item, i) => ...`, and a new item at its index re-runs only the holes that call `item()`. Rows leave from the end. Its runtime is `__index` in `@reactre/core/features/index`, which turns the compiled spec into a keyed one over positions, each a signal; the compiler imports it for a file that has such a list, so an app without one ships none of it. `keyed={(item) => key}` is `key`. The new `For` overloads are in a `// #if TYPES` block, which every build strips, so the size profiles are the same code as before, byte for byte, minified too; `test/features.test.ts` adds an `index` profile.
- Added: `memo(fn, { lazy, unobserved, equals })` and `signal(value | fn, { unobserved, equals })` in `@reactre/core/features/memo`: Solid 2.0's two options that need a count of a signal's readers. A lazy memo runs `fn` first when it is first read, not when it is made; once nothing reads it, it stops following its sources, keeping its value, and the next read runs `fn` again. `unobserved` is called when the last reader stops reading. The compiler sends a call that passes either option, or options it cannot read (a variable, a spread, a computed key), to the module's reader-counting entries (`__observedMemo`, `__observedSignal`), and so does a use of `memo` or `signal` it cannot follow to a call (passed as a value, exported, re-exported by name); every other call stays as it was. It reads each file alone, so a dev server and a build give the same code, in a .tsx or .jsx file with or without JSX, and in a server build. A call the plugin does not compile (a .ts file, a dependency) reaches `memo` and `signal` themselves: their development build (the sources, and the new `dist/dev/features/memo.js`, which the plugins pick as they pick the core's) throws for either option, naming the plugin and its `include` option, and production builds strip that check, with the new types, from `features/memo.ts` as they strip the core's development and type blocks. The compiler's Bun plugin loads a `.ts` file its `filter` takes as TypeScript. Only the signals made through the entries are counted: the array of their readers is of a subclass that sees the core push and splice readers, set on the signal once, as it is made, and nothing in the core checks for it, so `memo`, `signal` and the core's signals do the same work as before. Where they differ from Solid 2.0: the count is taken in a microtask after the last reader left, as a reader that runs again drops its reads before it reads anew, so `unobserved` runs then, and a lazy memo stops then, if no reader came back; a read outside any reader computes a lazy memo, which stops at the next microtask; and a lazy memo whose owner was disposed returns its last value. The entries are in a file of their own, `src/observed.ts`, re-exported by `features/memo`, so an app that passes neither option bundles the same code as before, byte for byte, minified too: every size profile is unchanged. `test/features.test.ts` adds a `lazyMemo` profile (7,712 bytes, 3,388 gzipped).
- Added: a development build, `dist/dev`, which the `"development"` export condition now resolves (it resolved `dist/async`; the development build has the async runtime too). It warns, with a code and a fix, about mistakes that render without an error: `REACTIVE_WRITE_IN_OWNED_SCOPE` (a signal written while a memo, a template hole or a `<For>` row's hole computes its value), `FOR_DUPLICATE_KEY` and `FOR_UNSTABLE_KEY` (two items of one key; an item whose key changed since the last render), `FUNCTION_AS_TEXT` (`{count}` for `{count()}`), and `ATTRIBUTE_HANDLER` (a function in a lowercase `on*` spread prop, which becomes an attribute's text), each once per thing it is found in. A `<For>` row's hole that writes a signal it reads throws `FOR_ROW_LOOP` after 100 rounds, as an effect that never settles does, where the production build overflows the stack.
- Changed: the checks sit between `// #if DEV` markers in `src/index.ts`, and `src/withoutAsync.ts` strips blocks by name (`strip(source, names)`, `without(...names)`; `stripAsync` and `withoutAsync` are as they were, `withoutAsync` now stripping every block the default build leaves out). `dist/` and `dist/async/` are built without them, so the default build's code is the same as before, byte for byte, and so is every size profile; `dist/async/` is the same code too. `bun run` and `bun test` run the sources, with the checks. `test/features.test.ts` adds a `dev` entry, the benchmark app with the development build: a size note.
- Fixed: a `<For>` row holding a slot, a component or a nested list wrote a later hole into the wrong node: the hole's node was looked up after those had put nodes in the row. `<li><Show when={true}><b>+</b><b>+</b></Show>{title()}</li>` kept its first title, and a component followed by a nested `<For>` put the list's rows among the component's nodes. A row with mounts now finds its holes when it is made.
- Added: server rendering, in `@reactre/core/server`. `renderToString(app)` renders an app compiled for the server (see @reactre/compiler and @reactre/plugin below) to HTML at once, a `<Loading>` that waits showing its fallback; `renderToStream(app)` returns a `ReadableStream` of the shell, once what it reads outside every `<Loading>` is ready, and then of each boundary's content as its data comes, in a `<template>` with a script that swaps it in for the fallback; `renderToStringAsync(app)` waits for all of it. Signals, memos, stores, context and `<Errored>` (which renders its fallback when its children throw) work as in the browser; effects do not run, memos compute when read, and `<Portal>` renders nothing. `isServer` is true there and false in a browser bundle, which resolves the module to a stub. Options: `hydrate` writes comment markers for hydration (`<!--[-->`/`<!--]-->` around what may change, `<!---->` between a text hole and text beside it, `<!--rr:e-->` before an `<Errored>`'s fallback, `<!--rr:b-->` around a `<Loading>`'s fallback `renderToString` wrote), `nonce` is set on the stream's scripts, and `onError` gets an error thrown after the shell was sent; the stream's swap script calls `self.$rrh(id)`, if a page set it, once it has put a boundary's content in. `@reactre/core/server/async` and `/server/dynamic` are the server's versions of the feature modules that touch the DOM themselves, and `/server/reaction`, `/server/timing`, `/server/errors` and `/server/effects` of those whose effects do not run there (`reaction`'s apply half, `onSettled`, `effect(fn, { error })`, `bind`'s apply, `autorun`, `onFlush`), which a server build points the app's imports at. The module's own `effect` does not run either. A spread's key that is not one attribute name (empty, or with whitespace, a control character, a quote, `<`, `>`, `/` or `=`) is left out, as in Solid 2.0, and a `<Dynamic>` or `dynamic()` tag that is not one element name throws, so neither can write markup of its own.
- Changed: nothing for a client bundle. The server's code is in its own entry, which imports the core as the feature modules do: `src/index.ts` and the feature modules are unchanged, and so is every size profile in `sizes.json`, byte for byte.
- Added: Solid 2.0's render effects, tracked effects and `onFlush` in `@reactre/core/features/effects`, as `bind`, `autorun` and `onFlush`. `bind(compute, apply, { defer, schedule })` is `createRenderEffect`: `compute(prev)` is tracked, `apply(value, prev)` runs untracked after each of its runs, at once where it is made (in a component, while the view is built), and a function it returns is a cleanup; `defer` skips the first apply, `schedule` makes it wait for the flush. `autorun(fn)` is `createTrackedEffect`: `fn` runs tracked, its first run waiting for the flush (the end of the batch it was called in, or else the next `flush()` or batch end, or a microtask), so in a component once the view is in the page; a function it returns is a cleanup. `onFlush(fn)` runs `fn` in a microtask after the work under way, the callbacks of one microtask in one batch, so their writes are an update of their own. A cleanup that is neither a function nor undefined throws. On the server no effect runs: a server build points the app's imports of the module at `@reactre/core/server/effects`, where `bind` computes and never applies, and `autorun` and `onFlush` never run.
- Added: Solid 2.0's list functions in `@reactre/core/features/lists`: `map(list, fn, { keyed, fallback })`, its `mapArray`, and `repeat(count, fn, { from, fallback })`. Each row is mapped once, untracked, under an owner of its own, disposed when it leaves; `map` keeps rows by the item (with an index accessor), by a key function (with item and index accessors) or by position (`keyed: false`, with an item accessor), and its array is the same when its rows are. An update whose map function throws changes nothing.
- Changed: nothing for an app that imports neither: both are built from the core's API and the batch queue features/timing reads, and every existing size profile is the same, byte for byte. `test/features.test.ts` adds two profiles, `effects` (3,303 bytes gzipped) and `lists` (3,849). 16 more of the Solid ports pass with them (`plans/solid-parity.md`).
- Added: hydration, in `@reactre/core/features/hydrate`. `hydrate(view, el)` runs the view over the HTML the server rendered into `el` with `hydrate: true`, keeping the server's nodes and attaching the view's holes, handlers, refs and effects to them, and returns its disposer; `isHydrating()` is true while code claims the page. A context's provider, an `<Errored>` that showed its fallback on the server (shown on the client too; `reset` builds the children) and a `<Loading>` whose children the server rendered are claimed too, through `@reactre/core/hydrate/errors` and `/hydrate/async`, which a hydrate build points the app's imports of `features/errors` and `features/async` at. No data goes from the server to the client: the client reads its async data again, and until a value comes what reads it keeps the server's nodes, with no fallback shown. A `<Loading>` whose fallback `renderToString` wrote is built afresh; one a stream has not sent keeps the server's fallback and hydrates when its content is swapped in. Where the page does not match, the nearest slot, list row or streamed boundary renders afresh (outside every slot, the whole view), and the development build (the new `dist/dev/features/hydrate.js`, which the plugins pick as they pick the core's) warns, `HYDRATION_MISMATCH`. `hydrate` over code not compiled for it throws, naming @reactre/plugin's `hydrate: true` option, and over a page without the markers, where the view needs them, names `renderToString(app, { hydrate: true })`. The server's errors stay out of the page in production: the `<Errored>` marker names the error and gives its message (escaped) only from the server's development build, and in production the client's fallback gets an `Error` saying the server's error was kept out of the page and that the development build shows it.
- Added: a development build of the server, `dist/dev/server.js`, which the `"development"` export condition of `@reactre/core/server` now resolves (Vite's dev server's `ssrLoadModule` gets it); `dist/server.js` is built without the server's `// #if DEV` block. Both plugins give a production build the stripped one whatever the conditions resolved, and strip the sources as they strip `index.ts`. The browser's builds, and so every size profile, are unchanged.
- Changed: nothing for an app that does not hydrate. `src/index.ts` is unchanged, and every size profile is the same code, byte for byte, minified and with names kept; `test/features.test.ts` adds a `hydrate` profile, the `plain` app hydrating (19,032 bytes, 7,715 gzipped, against `plain`'s 13,563 and 5,840).
- Added: `<For>` and `<Repeat>` anywhere, with rows of any shape, as Solid 2.0 has them: a list that is a component's whole view, a fragment's child beside other children, the only child of `<Show>`, `<Switch>`, `<Errored>`, `<Loading>` or a context's provider, or a row of another list; and rows that are text, fragments, arrays, nothing, a component whatever it returns, or an expression that may change, which is a slot. A keyed row function of two parameters gets an accessor of its index, and `<Repeat>`'s children that are not a function are each row's. Its runtime is `__each` in `@reactre/core/features/for`, which the compiler imports for a file that has such a list: the list is its nodes between two markers of its own, so it goes where content goes; a row is its content under an owner of its own, kept by key (an item new for its key builds its row again) or by position (`keyed={false}`, with an item accessor), and a render moves only the nodes not in place. `@reactre/core/hydrate/for` is the module in a hydrate build: its first render claims the server's rows in order, from one pair of markers, and builds afresh from a row that does not match.
- Changed: nothing for an app whose lists are all of element rows in an element, which still compile to the core's list: every size profile is the same code, byte for byte, minified and with names kept, and `features/hydrate` is unchanged. An app that uses the new module ships it, about 1.3 KB gzipped beside the core's list (an app whose lists are all its own ships it instead of the core's). The `For` overloads (a `// #if TYPES` block) and `<Repeat>`'s type take rows of any content and a keyed row's index accessor. 89 more of the Solid ports pass (`row-shape`, `for-placement`, `for-index`).
- Added: Solid 2.0's development messages and misuse errors, in the development build alone. An effect, a memo, a root or a slot made in an `autorun`'s function or in an `onSettled` callback that has an owner throws `PRIMITIVE_IN_FORBIDDEN_SCOPE`, and `onCleanup` there `CLEANUP_IN_FORBIDDEN_SCOPE` (return the cleanup instead); `flush()` in such an `onSettled` callback throws `FLUSH_IN_SETTLED`; an `onSettled` callback or a `reaction`'s `apply` that returns something other than a function or `undefined` throws `INVALID_CLEANUP`, and an `onSettled` callback outside any owner that returns a cleanup throws `SETTLED_CLEANUP_UNOWNED`. `useContext`'s `ContextNotFoundError` says which case it is: `CONTEXT_NOT_FOUND`, naming the context, or `CONTEXT_PROVIDED_UNDEFINED`, a provider of `undefined`. - Added: `@reactre/compat/server`, React 19.3.1's server rendering API: `renderToString`, `renderToStaticMarkup`, `renderToReadableStream` and `renderToPipeableStream` write the HTML React's production build writes, byte for byte, running compat's own hooks. `prerender`, `prerenderToNodeStream`, `resume` and `resumeToPipeableStream` are exported so imports resolve, and throw: compat does not implement partial prerendering. The README lists what else differs.
- Fixed: the class build (`@reactre/compat/classes`) is declared as having side effects, so bundlers that trust `sideEffects`, such as Vite's, keep the code that installs class support.
- Fixed: when an update arrives while a commit renders, its refs and layout effects still run before its passive effects, as in React (cmdk's list height).
- Fixed: a `<noscript>` renders its children only as text, as React does (input-otp's fallback style).
- Fixed: content a settled promise reveals inside `<Suspense>` waits until 300 ms after the last fallback appeared, as React throttles it (jotai's async atoms).
- Fixed: `useState` calls a lazy initial state with no arguments, as React does, instead of passing it itself (Apollo Client's `useQuery`).
- Fixed: keyboard events give `key`, `keyCode`, `charCode` and `which` as React does: `which` is the key code on keydown and keyup and the character code on keypress, and older key names are normalized (react-colorful's arrow keys). A field an event holds as its own without enumerating it, as events built with `Object.defineProperty` do, no longer goes missing.
- Fixed: a `<title>` rendered anywhere goes into `<head>` before the titles already there, as React places it, so the newest one sets the document's title (react-helmet-async's nested titles).
- Fixed: a new `<img>` gets `srcSet` and `src` after its other props, as React sets them, so attributes such as `sizes` and `loading` apply before the image is requested (react-image-crop's markup).
- Fixed: class components: `setState` in `componentWillMount` applies before the first render with no second render after it, and a class with a `getSnapshotBeforeUpdate` method gets no `componentWillMount` call, as in React.
- Fixed: hooks follow React 19's rules:
  - Deps arrays of another length compare on their common part.
  - An effect keeps each render's deps.
  - `useEffectEvent` returns a new function each render and throws when called during rendering.
  - `cache` returns a wrapper.
  - `useId` counts across all roots, as React's one client counter does.
  - A passive cleanup that throws after its component is removed goes to the error boundary above the removed subtree, or to the root, which unmounts and calls `onUncaughtError`. An error from a sync render's passive effects renders before `flushSync` returns.
- Fixed: a DOM error while placing nodes goes to the error boundary above, or to the root, which unmounts and reports it, as React captures a commit-phase error. The flush goes on to render the other updates queued with it.
- Fixed: `onCaughtError` runs before `componentDidCatch` and is given the boundary as `errorBoundary`. An error that `onCaughtError` or `onUncaughtError` throws is thrown again from a task of its own, and without `onUncaughtError` an uncaught error falls back to a task when `reportError` is missing.
- Fixed: on an update, each component's insertion effect cleanups, insertion effects and layout effect cleanups run together, children first, as in React's mutation phase.
- Fixed: `requestFormReset` resets at the next commit, after the transition it was made in ends, as React's state update of the form does, and throws React's error for a form React did not render.
- Changed: `flushSync` renders sync-lane updates only, as React's does: an update made outside an event waits for its own task, unless a sync update reaches the same component.
- Added: `browser()` from React 19.3: `use()` reads its token as undefined on the client. `use()` of anything but a promise, a context or that token throws React's error.
- Added: Fragment refs from React 19.3: a ref on a `<Fragment>` gets a FragmentInstance whose `addEventListener`, `removeEventListener`, `dispatchEvent`, `focus`, `focusLast`, `blur`, `observeUsing`, `unobserveUsing`, `getClientRects`, `getRootNode`, `compareDocumentPosition` and `scrollIntoView` work as react-dom's do on the fragment's visible top-level nodes. A node that mounts or shows in the fragment gets its listeners and observers, and loses them when it unmounts or hides. The code comes with the `Fragment` export, so an app that never imports `Fragment` leaves it out.
- Fixed: a render that throws is unwound to its boundary before the commit's layout effects run, as React renders the boundary within the same render. Content that suspends again commits nothing of the render that suspended: its layout effects and refs run when it shows.
- Fixed: `autoFocus` focuses only a `<button>`, `<input>`, `<select>` or `<textarea>`, as React does.
- Fixed: a `<Context.Consumer>` calls its children whatever they are, so children that are not a function throw, as in React.
- Fixed: an element rendered as a type is named in the error as React names its type, and a client reference has no name.
- Fixed: `useActionState` queues actions as React does:
  - The first action runs inside `dispatch`; the others wait for it.
  - In a transition, `isPending` is true until the queue drains, and the state is the last action's result.
  - Outside a transition, there is no pending state: the component suspends until the action finishes.
  - An action that fails rejects the actions queued after it, none of which runs, and its error reaches the error boundary once. Dispatch does nothing until a new action is rendered.
- Fixed: hidden content follows React's Offscreen rules:
  - A hidden `<Activity>` commits no effects, refs or class lifecycles, from its first render to the render that shows it.
  - Hiding runs every layout cleanup, ref detach and `componentWillUnmount`, parent first, then every passive cleanup.
  - Showing runs each effect once, children first, and attaches the refs and calls `componentDidMount` again.
  - An Activity inside hidden content waits for that content.
  - Shown content that suspends again has its layout effects and refs cleaned up until it is revealed, and its passive effects stay connected.
- Fixed: `unstable_batchedUpdates` is `fn(a)`, as React 19's is: updates outside an event render when the scheduler runs them.
- Fixed: a transition callback that throws synchronously sends the error to the component's error boundary (`useTransition`), or reports it (`startTransition`), instead of throwing to the caller.
- Fixed: a class's ref is detached before its `componentWillUnmount` runs, and either can throw without stopping the other. A callback ref to a class instance may return a cleanup, which runs instead of a call with `null`.
- Fixed: an element made by React 18 or older (`react.element`) is not a valid element and throws React 19's error when rendered. React's messages and hints are used for an invalid element type, and an object of another class rendered as a child is named by its tag, such as `[object Date]`.
- Fixed: events follow react-dom's rules:
  - `onChangeCapture` runs in the bubble phase with `onChange`, after the other bubble handlers.
  - `onChange` fires only for text fields (React's list of input types), checkboxes, radios, selects, file inputs and custom elements. A `change` event on a text field fires it when the value moved.
  - A non-bubbling event such as `load` runs the handlers of every element up the tree, and its capture handlers run in the capture phase. Elements React listens on, such as an `<img>`, need no handler of their own for that.
  - The far end of an enter or leave event from outside the root is the window.
  - `isDefaultPrevented()` is true after `preventDefault()`, even for an event that cannot be canceled.
- Fixed: the resource hints follow react-dom's rules:
  - `preconnect` keys on `crossOrigin` too.
  - `preload` needs an `as`, always fetches fonts with CORS, and passes `integrity`, `nonce`, `referrerPolicy`, `imageSrcSet`, `imageSizes` and `media` on.
  - `preinit` needs `as: "style"` or `as: "script"`. A stylesheet gets `data-precedence` and goes after the last one of its precedence.
  - `preinitModule`'s script is async.
  - A stylesheet or script takes what it lacks from an earlier preload of it.
  - Without a document, every hint does nothing.
- Fixed: element props follow React 19's rules:
  - Boolean attributes use React's list by prop name, `credentialless` included, and are present for any truthy value.
  - `muted`, `multiple` and an `<option>`'s `selected` are set as properties only.
  - An empty `src`, or an empty `href` off an `<a>`, is left out.
  - `cols`, `rows`, `size` and `span` need a number of at least 1, and `rowSpan` and `start` need a number.
  - `innerText` and `textContent` props are ignored.
  - `xlink*` and `xml*` props are namespaced on every element.
  - A `javascript:` URL in `src`, `href`, `action`, `formAction` or `xlinkHref` is replaced by one that throws, as React blocks it.
  - A custom element takes any value through a property it defines, strings and `undefined` included.
  - A custom element's own `on*` function props, such as `onMyEvent`, are native listeners for the event named after "on"; React's event props stay synthetic.
  - A prop starting with "on", in any case, is never an attribute of a built-in element.
- Fixed: styles follow React 19's rules: a string `style` throws, React's own list decides which numbers get `px`, and string values are trimmed.
- Fixed: form fields follow React 19's rules:
  - A boolean `value` is written as text.
  - An uncontrolled `<textarea>`'s `defaultValue` updates its default.
  - A controlled `<textarea>` with a `defaultValue` keeps it as its default.
  - A `<select>` with no matching option selects its first enabled one.
  - A `<select>`'s `defaultValue` also sets its options' `defaultSelected`.
  - A change of `multiple` with no `value` applies the `defaultValue` again or clears the selection.
- Changed: an update made outside React's event handlers renders as React's lanes order it: in a microtask during a discrete event such as a click or a key, and otherwise (timers, promises, continuous events such as mouseover) in a task of its own, so updates from timers that fire one after another render together (react-tooltip moving between anchors).
- Added: an ES module build of `@reactre/compat/compiler` in `dist/`, so Node can load `compileJs`.
- Docs: setting up Vite, with @reactre/plugin or an alias.

### @reactre/preact

- Added: first release. Preact 11.1.0's API and behaviour, its renderer, hooks and compat layer ported, on reactre's templates: `@reactre/preact/core` stands in for `preact` and `preact/hooks`, `/compat` for `preact/compat` and `react`, and `/jsx-runtime` for the JSX runtimes. `/compiler` (a Bun plugin) and `/plugin` (Vite, Rollup, Rolldown, esbuild, webpack and Rspack, under Node and Bun) compile JSX element trees into templates, and their `off` option switches APIs off one by one or by group, such as `@classes`; the build fails where a module uses a switched-off API, or reads the module in a way it cannot follow. `html` writes templates in plain JavaScript with no build step, and `/dom` is the DOM-only build: templates and events, no components.

## [0.0.1] - 2026-10-29

First release.

### @reactre/dom

- Templates parsed once and cloned, with typed holes for text, classes, attributes, properties, events and slots.
- A keyed `List` that reuses rows and makes the fewest DOM moves, and `morph`.

### @reactre/core

- Signals, effects, `memo`, `batch`, `untrack` and a keyed `selector`.
- `<For>` keyed lists and `render` for TSX views compiled by @reactre/compiler, on @reactre/dom's templates.

### @reactre/compiler

- A Bun plugin that compiles reactre TSX into templates and the code that updates them.

### @reactre/compat

- React 19's client API on @reactre/dom's templates: hooks, context, memo, refs, portals, Suspense and lazy, transitions, synthetic events, controlled fields and hydration.
- `@reactre/compat/classes` for class components, and `@reactre/compat/compiler`, a Bun plugin that compiles host JSX trees to templates.

All packages ship ES modules for browsers and bundlers, and TypeScript sources for types.

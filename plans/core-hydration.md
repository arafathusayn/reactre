# Hydrating server-rendered HTML

`@reactre/core/server` renders an app to HTML (`renderToString`, `renderToStream`, `renderToStringAsync`). With hydration the client does not render the page afresh: `hydrate(App, el)` from `@reactre/core/features/hydrate` claims the nodes the server sent, attaching the client's holes, effects, handlers and refs to them, so the page is interactive without building its DOM twice. This note is the design, as built; the decisions it made are marked as such.

## The rule it keeps

An app that does not hydrate ships nothing for it, byte for byte, as with SSR itself. Every size profile in [sizes.json](../packages/core/sizes.json) is the same bytes as before hydration existed, minified and with names kept, and the js-framework-benchmark app compiles to the same code; the `hydrate` profile is what hydration adds. So hydration is a compile mode and modules of its own, not a branch in the code every app runs:

- **Compile mode.** `@reactre/compiler`'s `hydrate` compile option (`compileJs(js, { hydrate: true })`, and the Bun plugin's `reactreCompiler({ hydrate: true })`). Without it, the output is what it was. With it, a template's code claims the page's element at a cursor instead of cloning (`__hclone`), slots and lists claim the nodes between their markers (`__hslot`, `__hinsert`, `__hfor`), a fragment passes what it builds as functions in order, a `<Portal>` builds its children in its mount (`__hportal`), and a `<Dynamic>` element claims its tag (`__hel`, `__hkids`). The helpers come from `@reactre/core/features/hydrate`, which no other build imports.
- **Decision: the plugin's option.** `@reactre/plugin` has a `hydrate: true` option of its own, not part of `ssr: true`: with `ssr` outside Vite every build is a server build, and an app that renders on the server may not want hydration. In Vite, `ssr` and `hydrate` together make the server's environment render and the client's hydrate. Misused, the option fails, naming itself: with `compat`, and with `ssr` in another bundler.
- **The core's feature modules.** A context's provider, an `<Errored>` and a `<Loading>` build their content with the core's `__frag`. A hydrate build loads the core's feature modules with `@reactre/core/features/hydrate` for the core (both plugins do it, `hydrateImports(code, false)`), and that module re-exports the core with a `__frag` that claims. The core's `index.ts` is not changed.
- **Failing clearly.** `hydrate` over code compiled without the mode throws, naming the plugin's option (its templates clone, so nothing is claimed); a file that imports `hydrate` and is compiled without the mode fails to compile, naming it too. A page rendered without the markers, where a slot's content needs them, throws naming `renderToString(app, { hydrate: true })`. A page with the markers that does not match falls back, slot by slot (see mismatches).

## The markers the server writes

With `renderToString(app, { hydrate: true })` (or `renderToStream`'s, or `renderToStringAsync`'s), the HTML carries comment markers wherever the client's DOM has structure that the markup alone does not show. Without the option, none are written.

| Marker                             | Where                                                                                                                 | What it lets the client do                                                                                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<!--[-->` ... `<!--]-->`          | Around every slot (a hole that may hold nodes, `<Show>`, `<Switch>`, `<Dynamic>`), every list, and a `<For>` fallback | Know a slot's nodes: the slot's effect adopts the nodes between the pair, and its next content replaces them. A list's rows are the nodes between its pair. |
| `<!--[-->` ... `<!--]-->`          | Around each function child of a fragment (a context provider's or an `<Errored>`'s children)                          | The same, for the owned effect that builds those children on the client.                                                                                    |
| `<!--[-->` ... `<!--]-->`          | Around a list of `features/for` (one outside an element, or whose rows are not one element), rows or fallback inside  | The list renders between the pair; its first render claims its rows in order. A row that may change has a pair of its own, its slot's.                      |
| `<!---->`                          | Between a text hole and static text or another text hole beside it                                                    | The HTML parser merges adjacent text into one node; the marker keeps the hole's text a node of its own, which the client's text binding can take as it is.  |
| `<!--rr:e-->`                      | Before an `<Errored>`'s fallback that the server showed (`@reactre/core/server/errors`)                               | Show the fallback too, claiming the server's nodes, with an Error saying the server's error was kept out of the page.                                       |
| `<!--rr:e:NAME:MESSAGE-->`         | The same, from the server's development build                                                                         | The same, with an error of that name and message.                                                                                                           |
| `<!--rr:b-->` ... `<!--/rr:b-->`   | Around a `<Loading>`'s fallback that `renderToString` showed                                                          | Build that boundary afresh: it shows its own fallback until its data comes.                                                                                 |
| `<!--rr:bN-->` ... `<!--/rr:bN-->` | Around a streamed `<Loading>`'s fallback, until its content comes                                                     | The swap script finds the fallback to replace; then it calls `self.$rrh(N)`, and the boundary hydrates its content.                                         |
| `<template id="rr:tN">`, `$rr(N)`  | A streamed boundary's content, and the script that swaps it in                                                        | Nothing for hydration: the template is removed when it is swapped in.                                                                                       |
| `<script>$rrv({...})</script>`     | After the shell, before a streamed boundary's template, at the end: the values the render's hydration writer wrote    | `takeHydrationValue(key)` takes a value from `self.$rrd`; a Promise's value arrives in a later one (see Async data, below).                                 |

Static markup needs no marker: the client's paths through a template are the same over the server's markup, as both come from the same JSX. A component leaves no trace in the markup, as it leaves none in the DOM.

**Decision: the server's errors stay out of the page in production.** An `<Errored>`'s marker names the error and gives its message only in the server's development build (a `// #if DEV` block in `src/server.ts`, as the core's diagnostics are), so a production page's source holds nothing of the server's internals, a message holding `</script>` included (the development build's marker escapes it). The client's fallback then gets an `Error` whose message says the server's error was kept out, and that the development build shows it; `reset` builds the children as before. A fallback that shows `err.message` shows that one on the client in production: an app should render a message of its own there. The server's builds are picked as the core's are: `dist/server.js` is built without the block and `dist/dev/server.js` with it, which the `"development"` export condition resolves, so Vite's dev server's `ssrLoadModule` renders with the development build; @reactre/plugin and the compiler's Bun plugin give every production build the stripped one, whatever the conditions resolved, and strip the sources (the `bun` condition) as they strip `index.ts`. `bun run` and `bun test` run the sources as they are, as the development build.

## Claiming

- **Templates.** The compiled code checks the page's element against the template's prototype, side by side, and finds each hole's node where a clone's would be: an element's attribute and property holes bind to the element; a text hole takes its text node (an empty one is missing in the HTML, and is made and inserted there); formatting whitespace between tags is passed over. A constant value the page does not have is written. A reactive hole's value starts undefined, so the page's value stays until its bind writes one: an async value that is not ready yet writes none.
- **Slots.** A slot's first run claims the nodes between its markers, which stay as its anchors; its later runs put their content there, keeping the nodes that are already in place.
- **Lists.** The rows are between one pair of markers, in the order of `each`. The list's first render claims a row per item, in order, by the row's template; a list with a fallback has two pairs, the list's and the fallback's.
- **Lists of any shape. Decision: a module of their own.** A list of `@reactre/core/features/for` (a component's whole view, a fragment's or control flow's child, rows of text, fragments or content that changes) claims through `@reactre/core/hydrate/for`, where the compiler's hydrate mode imports the list from, so `features/hydrate` stays as it was, byte for byte. Its rows, or its fallback, are in one pair; a row's content claims its nodes as content does (text the HTML parser joined with the next row's is split), and from the first row that does not match the rest are built afresh. Where the page has no pair at all, the nearest slot renders afresh.
- **Context and boundaries.** A provider's children claim within its pair. An `<Errored>` whose server render showed its fallback hydrates its fallback (`@reactre/core/hydrate/errors`): its children's first build throws the server's error, its fallback claims the server's nodes, and `reset` builds the children afresh.
- **Async data. Decision: data goes from the server to the client by a key the app gives, and only then.** The server render's hydration writer (`getHydrationWriter()`) and `takeHydrationValue(key)` in the browser are the path: a value written under a key goes into the page (`self.$rrd`, below), and the client takes it out by the same key. An async memo with an `id` option uses it: in a render with `hydrate: true` that waits (`renderToStream`, `renderToStringAsync`), the server writes the memo's first value (a Promise, sent as pending and then settled) under the id, and the hydrating client's memo takes it as its first value instead of computing it, running `fn` once with `fetch` stubbed to learn what it reads (`@reactre/core/hydrate/async`); `ssrSource`, `deferStream` and `transparent` say what each side does with it. Solid keys each memo by its owner's id, which every owner there has; reactre's owners have none, and a key made from a memo's place in the tree would differ between the server and the client wherever the two make different owners (a `<Show>` branch, a list, a boundary), so the key is the app's. A memo without an id is as before: the client computes it again, and while it waits the boundary keeps the server's nodes (the runs that wait do not count for a boundary while it hydrates, so it never shows its fallback over the server's content). A `<Loading>` whose fallback the server showed is built afresh. None of this changed the markers.
- **Hydration values. Decision: data, never code, in the page.** Each flush of values is a `<script>` with the render's `nonce` that calls `$rrv({...})`, which a first script defines, into `self.$rrd`, a registry of no prototype: with the shell, before each streamed boundary's template (its hydration reads them), and at the end. The values are JSON, a subset of JavaScript expressions, with `<`, `>`, `&`, U+2028 and U+2029 written as unicode escapes in strings (the only place JSON has them), so no value ends the script or opens a comment. A key named `__proto__`, the writer's or an object's in a value, is refused, as an object literal would take it as a prototype; what JSON has not (undefined, NaN, the infinities, -0, a bigint, a Date, a Map, a Set, a plain object of a `$rr` key) is tagged as `{"$rr": tag}`, and what cannot be sent (a function, a symbol, a class's instance, a cycle) throws, naming the key, rather than arriving changed. A rejected Promise's error is named, with its message, only by the server's development build, as `<Errored>`'s marker is.
- **Streaming.** A boundary still streaming when `hydrate` runs keeps the server's fallback, and hydrates when its content is swapped in: the swap script calls `self.$rrh`, which the hydrate build of `<Loading>` sets, so each boundary hydrates on its own, as React's selective hydration does.

## Mismatches

Where the page does not have the node the code expects (a different tag, a missing node, other text, a marker where an element was expected), hydration stops claiming for the nearest slot (or list row, or streamed boundary) and renders its content afresh, replacing the nodes between its markers; the development build warns, `reactre HYDRATION_MISMATCH`. Outside every slot, the whole view renders afresh. Attribute values the server wrote and the client computes differently are set by the client's binding as it runs, as any update would.

## What the server does not write, and the client does

- Event handlers are not in the HTML (no inline handlers): hydration attaches them. A click before hydration is lost.
- `<select value>` is not written as `selected` on its option, and a `<textarea>`'s text is the server's: the client sets them as properties, which hydration does when it binds the hole.
- `<Portal>` renders nothing on the server: its children are built on the client, into its mount.
- Effects do not run on the server: on the client they run once at hydration, as on a first render.
- A `clientOnly` component is not rendered on the server, nor its module loaded: the server writes its fallback in a slot, which the client claims, and the component takes its place in a microtask after the page has hydrated.

## Known gaps

- A `<Dynamic>` whose tag is a runtime string and whose children change renders afresh (the server writes its children as plain content, the client as a slot); `dynamic()`'s components render afresh.
- The hydrate builds of `<Loading>` and `<Errored>` are built on the client's, which build their content off the page and put it in: the server's nodes are moved once, into the same place.
- Rows have no key marker each: a client whose list differs from the server's re-renders the rows from the first that does not match.

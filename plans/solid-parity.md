# Solid 2.0 parity, measured

836 of Solid 2.0's own tests (solid-js 2.0.0-rc.20, [solidjs/solid@5e68925](https://github.com/solidjs/solid/tree/5e68925cc2fd216a9fb06345019e66d5da5c523c)), ported to reactre's API in [`packages/core/test/solid/`](../packages/core/test/solid): **668 pass** (80%), and 168 fail because reactre lacks the capability or behaves differently.

The top gaps, by the ports they block:

1. **`action-writes`, 19**: an action holding and batching its plain writes until it ends.
2. **`held-writes`, 10**: reads and effects that see a write before `flush()`. By design (reactre applies writes at once), and counted once per file.
3. **`client-error-hook`, 9**: `configureClientErrors`/`render`'s `onError` hearing what a boundary caught.
4. **`dev-checks`, 7**: Solid's strict-read warnings in a component body, and its message for a component that is not a function: both need a component's body told apart from an app's `untrack`.
5. **`match-placement`, 6**: a `<For>` or `<Show>` of `<Match>`es in a `<Switch>`.
6. **`action-sync-yield`, 6**: a sync `yield` resuming at once.
7. **`create-reaction`, `dispose-order`, `owner-ids`, `portal-events`, `pull-memos`, `reconcile-identity`, `store-in-place`, `symbol-keys`, 5 each**.
8. **`bug`, 1**: one bug still open, [below](#bugs-found); eight more are fixed.

`glitch-free` (9) landed in the core: a write marks the memos it may change, then recomputes each once, after what it reads, so a diamond's join runs once per write, in Solid's order. Writes still apply at once (`held-writes`).

`row-shape` (58) and `for-placement` (30) landed as features/for: a `<For>` or `<Repeat>` stands anywhere content does, and its rows may be text, fragments, arrays, nothing or content that changes. Their ports pass, with each of Solid's list permutations (`1 missing`, `swaps`, `rotations`...), and so does `for-index`'s: a keyed row function of two parameters gets an index accessor.

`misuse-errors` (6) landed in the development build: Solid's errors for what an autorun's function or an owned `onSettled` callback makes, `flush()` there, and a cleanup that is not one. So did 8 of `dev-checks`: `ContextNotFoundError`'s messages and an `<Errored>` fallback's log.

`list-functions` (`mapArray`, `repeat`) and most of `render-effects` (`createRenderEffect` with `defer` and `schedule`, `createTrackedEffect`, `onFlush`) landed as feature modules, features/lists and features/effects, and their ports pass. What is left of `render-effects` is `reaction`'s, below.

`ssr-helpers` (`httpStatus`, `httpHeader`, `takeHydrationValue`, `getHydrationWriter`, 7), `client-only` (`clientOnly`, 4), `from` (3) and four of `memo-options` (`loadingValue`, `deferStream`; `transparent`, `ssrSource` and `id` too) landed in @reactre/core/server, features/hydrate and features/async, and their 18 ports pass. So did `ssr-semantics` (9), Solid's server semantics for its primitives: memos computed where they are made, `bind` applying once, `isPending` throwing on for data that has not come, `renderToString` throwing for it outside every `<Loading>`, and `action`, the optimistic setters and `deep` inert, in @reactre/core/server/actions and /server/store.

The other targets this set out to count: `memo-options` 0 (done: `reaction`'s `ssrSource` too), `store-path` 0 (done), `hydration` 4, `client-only` 0 (done), `from` 0 (done), `store-alias` 0 (done: the compiler follows a store through a local, a box, a function's result and a prop), and `jsx-props` 0 (no port found JSX in a prop that did not work: the ports pass JSX in `fallback`. A component's `{props.header}` given JSX was a text hole; it is inserted now, and a file compiled alone inserts every prop hole of a component it exports, as it may be passed JSX). [Gaps, by target](#gaps-by-target) lists all 61 targets and their tests.

## What was read

- **solid-js 2.0.0-rc.20** and **@solidjs/web 2.0.0-rc.20**, the npm `next` tags on 2026-11-01 (solid-js's `beta` tag is 1.10.0-beta.0, a 1.x line), and @solidjs/signals 2.0.0-rc.20, which solid-js re-exports. Their `gitHead` is [solidjs/solid@5e68925](https://github.com/solidjs/solid/tree/5e68925cc2fd216a9fb06345019e66d5da5c523c); the tests were read from the repository at that commit.
- The exports: solid-js's `types/index.d.ts` and `package.json` exports (`.`, `./refresh`, `./attribution`, `./internal`), @solidjs/web's `types/index.d.ts`, `index.server.d.ts`, `client.d.ts`, `server.d.ts`, `server-mock.d.ts`, `response.d.ts` and its subpaths (`./jsx-runtime`, `./storage`, `./serialization`, `./server-functions/*`, `./frames/*`, `./performance-tracks`).
- Nothing downloaded was run: the tarballs were read as data.

Parity here means Solid's capabilities, not its names: reactre keeps its own (`signal`, `memo`, `effect`, `reaction`) and puts runtime APIs in feature modules under `@reactre/core/features/*`. Of the names it chose: `bind` (createRenderEffect) because a render effect is a value bound to a write, what a compiled hole is (`__bind`); `autorun` (createTrackedEffect) because it is MobX's one-function effect, beside `reaction`, MobX's two-half one, which reactre already uses for createEffect; `map` (mapArray) as the short verb, `repeat` as Solid has it; `onFlush` beside `onCleanup` and `onSettled`, which keep Solid's names.

## Capability map

"Core, compiled" is in `@reactre/core` and compiled away by @reactre/compiler (an app that does not use it ships none of it); "core" is a runtime function of `@reactre/core`'s main entry; "feature" is an opt-in module, `@reactre/core/features/<name>`, that an app ships only if it imports it; "server" is `@reactre/core/server`.

## Bugs found

Where reactre claims a capability and the port shows it wrong. Each has `gap("bug", ...)` tests, which fail until it is fixed. Bugs 1, 2, 3, 5, 6, 7, 8 and 9 are fixed: their ports are plain tests now, and each has regression tests in the module's own test file.

1. **Fixed.** Core `memo` stores what its `fn` returns, a function too: a memo is no longer a signal written through its setter (glitch.test.ts "a memo stores what its function returns, a function too"). Was: **Core `memo` treats a function its `fn` returns as a setter's updater** (3 ports: signals "updates downstream pending computations", reconcile's two "replaces a TRACKED function-valued ... without invoking it"). `memo` stores `fn()` through `signal`'s setter, which calls any function it is given. The async build (`computed`) does not, so the two builds disagree. `reaction`, built on `memo`, has it too. features/memo's `memo` does not.
   ```ts
   import { memo } from "@reactre/core";
   const f = () => "called";
   memo(() => f)(); // "called"; expected f
   memo(() => () => 5)(); // 5 (typeof "number"); expected a function
   ```
2. **Fixed.** `reaction`'s effect now takes the live mark from its memo: once `compute` has read through `latest` or `isPending`, no transition holds `apply` (async.test.ts "a reaction whose compute reads through latest or isPending is not held"). Was: **`reaction`'s compute does not escape a transition through `latest` or `isPending`** (3 ports: memo's "should should show pending state in graph" and "should track pending value changes for loading indicator pattern", loading's "latest(asyncMemo) ... re-reports pending on each refresh (#2829)"). `latest` marks the current observer live, and in `reaction` that is the internal memo, not the effect that runs `apply`. The README says an effect that reads through `latest`/`isPending` is not held. With the async runtime on:
   ```ts
   const [s, set] = signal(1);
   const a = memo(() => Promise.resolve(s())); // features/async
   effect(() => void a());
   let r = 0, e = 0;
   reaction(() => latest(s), (v) => (r = v));
   effect(() => (e = latest(s)));
   await tick();
   set(2); // e === 2, r === 1
   ```
3. **Fixed.** An action called in another action's code settles its Promise when its generator ends, as Solid's always do; one called anywhere else still settles when the transition ends (actions.test.ts "an action called in another's code settles as it returns"). Was: **An action that yields another action's Promise never settles** (actions "should support yielding another action's promise"). The inner action joins the one open transition; its Promise waits for the transition, which waits for the outer action. The README says overlapping actions end together, not that they deadlock.
   ```ts
   const inner = action(function* () { yield Promise.resolve(); return 1; });
   await action(function* () { yield inner(); })(); // never resolves
   ```
4. **`<Show>` with a function child evaluates `when` twice per change** (show "Testing nonkeyed function show control flow > Toggle"). The compiler emits one memo for `!!when` and another for the accessor's value, and both run the expression; with plain children it runs once.
   ```tsx
   let n = 0; const [c, setC] = signal(0);
   attach(() => <div><Show when={(n++, c())}>{(v) => <span>{v()}</span>}</Show></div>, root);
   setC(7); // n === 3; Solid: 2
   ```
5. **Fixed.** `reconcile` on a shallow store replaces its values by reference, and re-runs their readers (store.test.ts "on a shallow store, it replaces the values"). Was: **`reconcile` on a shallow store merges into its raw rows and re-runs no reader** (store's two shallow.test.ts ports). A shallow store hands out raw values and tracks its own keys only, so a merge into the old row changes the caller's object and notifies nothing. The README says a shallow store's values are replaced.
   ```ts
   const [s, set] = createStore([{ v: 1 }], { shallow: true });
   effect(() => console.log(s[0]));
   set(reconcile([{ v: 2 }], null)); // logs nothing; s[0] is the old object, now { v: 2 }
   ```
6. **Fixed.** `@reactre/core/server`'s `effect` is the one that does not run, however an app reaches it (a named import, a namespace, a re-export), and a server build points the app's imports of features/reaction, timing and errors at server versions: `reaction` computes and never applies, and `onSettled` and errors' `effect(fn, { error })` never run. The feature modules whose own effects compute what they return (a projection, features/memo's derived signal, `resolve`, `until`) import the core's `effect`, which runs (`serverImports(code, false)`). features/effects has a server version too (server/effects.ts): `bind` computes and never applies, and `autorun` and `onFlush` never run; features/lists computes on the server as on the client. With it, the port of Solid's server `createRenderEffect`, "computes and runs effect once", is an `ssr-semantics` gap on `bind` (server.test.ts "effects on the server", "in a server build"). Was: **`reaction` runs its apply half during a server render** (server "runs compute but not effectFn on the server"). The README says effects do not run on the server. The server compile rewrites the app's own `effect` imports, but feature modules (features/reaction) get the real core `effect` through `@reactre/core/server`. In a server build: `reaction(() => 1, () => log.push("ran"))` in a component, then `renderToString`, logs "ran". Other feature modules' effects may do the same (not checked).
7. **Fixed.** The `<Loading>` boundary sent its content the moment the cell that threw was disposed, which was in the middle of `<Errored>`'s run that puts the fallback in its place. A boundary now sends what it has in a microtask after it stops waiting, through renderToStream and renderToStringAsync; renderToString, which cannot wait, writes `<Loading>`'s fallback for a rejection still to come and `<Errored>`'s for one already known (server.test.ts "`<Errored>` and async data", "in a server build"). Was: **On the server, `<Errored>` turns an async rejection into empty content** (3 server ports from ssr-async.spec and ssr-stream.spec). No fallback and no error: the stream ends with `<template id="rr:t0"><p></p></template>`. Without `<Errored>`, `renderToStringAsync` rejects with the error, as it should. In a server build:
   ```tsx
   const data = memo(() => Promise.reject(new Error("boom"))); // features/async
   <Loading fallback="L"><Errored fallback={(e) => <span>err {e.message}</span>}><p>{data()}</p></Errored></Loading>
   // renderToStringAsync: "<p></p>"; expected the fallback
   ```
8. **Fixed.** `__ssrAttrs` leaves out, as Solid does, a key that is empty or holds whitespace, a control character, `"`, `'`, `<`, `>`, `/` or `=`; the server compile throws for such a name written in the source (server.test.ts "the names the server writes", and the compiler's "names the server writes"). Was: **The server writes a spread's attribute names unchecked** (server "through a compiled spread"): a key can inject markup. The client's `setAttribute` throws for such a name; Solid drops it.
   ```ts
   __ssrAttrs({ "x><script>alert(1)</script": "" }); // ` x><script>alert(1)</script=""`
   ```
9. **Fixed.** `__ssrElement` (`<Dynamic>`, `dynamic()`) throws `"<tag>" is not a valid tag name`, on every render, for a tag that does not start with an ASCII letter or holds one of those characters; the server compile throws for one written in the source. `<Portal>` writes nothing on the server, so its `mount` never reaches the HTML (the same tests). Was: **The server writes a `<Dynamic>` tag name unchecked** (server "a tag that is not one HTML element name throws, on every render"): `<Dynamic component={tag()} />` with `"div x"` gives `<div x></div x>`. Solid throws "is not a valid tag name".

Found on the way, filed as gaps rather than bugs since reactre claims nothing about them, but worth a look:

- A cleanup that throws stops the teardown (`cleanup-throw`): the owner's later cleanups never run and its later children are never disposed, so they stay subscribed. `createRoot((d) => { onCleanup(() => log.push("owner")); reaction(() => 1, () => () => { throw e; }); return d; })()` throws and `log` stays empty.
- Fixed: a draft write of `__proto__`, or a `reconcile` of JSON with an own `__proto__` key, set that store object's prototype (`proto-guard`). It was worse than first filed: `reconcile(JSON.parse('{"__proto__": {"x": 1}}'))` merged into `Object.prototype` itself (the inherited `__proto__` read as the object to merge into), and so did a draft write through an inherited `__proto__` or `constructor` (`d.__proto__.x = 1`). Now, as in Solid 2.0, a draft write of `__proto__` is dropped; an inherited `__proto__` or `constructor` reads as undefined through a store or a draft; and an own `__proto__` (JSON's), from `reconcile`, a returned object or `snapshot`, is kept as own data (store.test.ts "\_\_proto\_\_ and constructor").
- Fixed: `packages/core/package.json`'s `sideEffects` listed `./src/features/*.ts` and not `./src/server/*.ts`, so in a server build a bare `import "@reactre/core/features/async"` (rewritten to `server/async`) could be dropped by the bundler, and an async memo then read as a Promise. It lists `./src/server/*.ts` and `./dist/server/*.js` now.

## How the ports are written

The ports are in [`packages/core/test/solid/`](../packages/core/test/solid), one file per area, and run in `bun test` with the rest. [`harness.ts`](../packages/core/test/solid/harness.ts) holds Solid's license and the rules:

- Each Solid `it` is one `test`, under Solid's name, in a `describe` named for its Solid file (Solid's own `describe`s kept inside). Each file's header names the Solid files it ports.
- Names are translated to reactre's (the map above), and each test keeps its intent and assertions. Where reactre has no such function, the port says how it was expressed (Solid's default keying by reference is `key={(x) => x}`; `render` returning a disposer is `attach`; an `Errored` fallback's `err()` accessor is `err`).
- TSX is compiled from strings by @reactre/compiler, as the plugin compiles it, and run on the fake DOM (`compile(src, modules, scope)`). The server ports that need a context provider or `<Errored>` on the server build the source with `Bun.build` and the compiler's Bun plugin in server mode, as a server build does, into a temp folder.
- Solid holds a write until `flush()`; reactre applies it at once, by design. `flush` (features/timing) is kept where Solid calls it. An assertion that a read or an effect has not yet seen a write is not repeated in every port that steps through one: each file has one `held-writes` test that collects them, so the design difference counts once per file.
- A port that fails because reactre lacks the capability or behaves differently is `gap(kind, why, name, fn)`: `test.failing` (Bun 1.4.4 has it), so it runs, must fail, and is reported once it passes; its name ends with `[kind: why]`. `SOLID_STRICT=1 bun test packages/core/test/solid` runs them as plain tests, to see why each fails; every one was checked to fail for its stated reason.
- The ports of `memo(fn, { lazy })` and `signal(v, { unobserved })` call `folded` in the harness: features/memo's reader-counting entries, which a call that passes either option compiles to. A port is TypeScript the compiler does not see, and `memo` and `signal` themselves throw for the options in the development build that `bun test` runs.
- Files that load features/async or features/actions turn the async runtime on before their tests and off after, as `../async.test.ts` does.
- When a capability lands, its `gap` tests start to pass and fail the run: make them plain `test`s and update the counts here. The counts come from a JUnit report: `bun test --reporter=junit --reporter-outfile=<file> packages/core/test/solid`, where a gap's name ends with `[kind: why]`.

Not ported: Solid's tests of its own machinery (attribution, lanes, held/verdict/landing internals, devtools and diagnostics records, dist artifacts, fuzzing, HMR), of server functions, frames, assets, cookies, request events and the serializer (missing as families, see the map), and most issue-numbered scheduling regressions. Each file's header and the agents' notes say what was read and skipped.
